# 设计文档

## 1. 总体结构

```
             ┌──────────────────────────── EditorApp (app.py) ────────────────────────────┐
             │  Tk 主窗口 · 工具栏 Toolbar · 画布 Canvas · 状态栏 · 播放循环 · 全部命令      │
             └───────┬───────────────────────┬───────────────────────┬────────────────────┘
                     │                       │                       │
             Document (model/document.py)   ViewState (ui/view.py)  AudioPlayer (audio.py)
             谱面 + 选择 + 剪贴板 + 撤销     屏幕↔拍换算 / 吸附 /      pygame.mixer 或
                                            缩放 / 几何布局           静音时钟 + 延迟补偿
                     │                       │
              Chart (model/chart.py)         │
              元数据 / 时间轴 / 设置 /        │
              速度组 / 物件                  │
                     │                       │
       TimingMap(拍↔秒) SpeedGroup(流速积分)  │
                     └───────────┬───────────┘
                                 │
                  Renderer (ui/renderer.py) → Scene (ui/scene.py) → Tk Canvas 图元
                  ToolController (ui/interactions.py) → Document 编辑命令
```

分层原则：

* `model/` 与界面完全解耦（可无界面运行、可单元测试）。
* `ui/` 只做“展示 + 交互 → 命令”，不保存谱面状态。
* 所有**谱面数据**的修改都经由 `Document`，因此撤销 / 脏标记 / 窗口标题完全一致；
  视图 / 编辑器设置是全局偏好（`settings.json`），直接改值，不参与撤销栈与脏标记。

## 2. 坐标与运动

### 2.1 三个坐标系

| 坐标系 | 单位 | 用途 |
| --- | --- | --- |
| 拍（beat） | 1 拍 = 时间网格的基本单位 | 一切物件的时间都用拍记录 |
| 秒（second） | 纵向映射的长度单位（判定线以上固定显示 `zoom_seconds` 秒） | 时间轴与物件高度 |
| 屏幕像素（px） | `每秒像素 = 判定线以上像素 / zoom_seconds`（常数） | 最终绘制 |

### 2.2 判定线永远吸附网格

`ViewState.current_beat` 是“判定线当前所在的拍”。
所有滚动 / 跳转 / 步进 / 缩放后都调用 `snap_beat(beat) = round(beat × division) / division`，
因此判定线总是落在时间网格线上，物件位置与网格严格一致。

### 2.3 网格（时间轴）映射：按秒线性

```
y(beat) = judgment_y − (秒数(beat) − 秒数(current_beat)) × 每秒像素
每秒像素 = (judgment_y − play_top) / zoom_seconds      ← 常数，只由缩放决定
```

* `zoom_seconds`（缩放）表示“屏幕上同时显示多长时间内的物件”；
* **每拍像素 = 每秒像素 × 该拍所在 BPM 段的秒每拍**：BPM 变更处之后的格子立刻变密 / 变疏，
  不必等判定线走到那里；判定线跨过 BPM 变更点时画面**不会整屏突变**（比例是常数）。
* 由此可得：**同样的时间间隔 = 同样的长度**；同样的拍数在越快的段落里越短。
  （因此“BPM 不影响物件速度”只对**拍空间**成立：`SpeedGroup.distance()` 仍然是拍积分。）

### 2.4 物件映射（速度组）

```
D(t)    = ∫_{t}^{t_judge} v(u) · spb(u) du   （“滚动秒数”：流速倍率 × 该段秒每拍）
y_note  = judgment_y − D(t) × 每秒像素
```

* 实现见 `SpeedGroup.scroll_seconds()`：流速段与 BPM 段都是分段常数，
  按两套边界的并集切开逐段累加（同段内走 O(1) 快速路径）；
* 判定时刻 `t = t_judge` 时 `D = 0`，物件一定在判定线上；
* `v ≡ 1` 时 `D` 就是两拍的秒数差，与网格映射完全一致（默认速度与时间轴网格严格对齐）；
* `v < 0` 时 `D` 变号 → 物件被“推”到判定线下方，形成反向特效；
* 段数极少，因此可以直接在每帧渲染中调用（4000 物件整帧实测 4.7 ms）。

### 2.5 非单调速度：不能用“拍差”做任何判断

流速列表允许正数、0 与负数，且各段叠加。于是 **物件的屏幕位置不是判定时刻的单调函数**：

* 远处（判定时刻相差很多拍）的物件可能被推回判定线上；
* 近处的物件可能被甩出画面，甚至跑到判定线下方很远处；
* 两个不同的判定时刻可能落在同一个屏幕位置。

例如 `v = 1 (0..10) → -1 (10..20) → 1 (20..)`：

```
判定线在 10 拍时，判定时刻 30 拍的物件：D = ∫₁₀³⁰ v = -10 + 10 = 0 → 正好落在判定线上
判定线在 10 拍时，判定时刻 20 拍的物件：D = -10              → 被推到判定线下方
```

因此实现遵守两条硬性约束：

1. **可见性剔除只按算出来的像素位置**（`ui/renderer.py::_draw_notes` 先算 y 再决定是否绘制），
   绝不用“拍差大于阈值就跳过”这类粗暴判断；
2. **命中测试与渲染共用同一套几何**（`ui/geometry.py`），保证“看到的”就是“点得到的”。

空域的上下边界随流速变化，必须在速度段边界处取折点，否则折点会被直线糊掉：
`geometry.sample_beats()` 会强制把落在区间内的速度段起点加入采样点，渲染与命中测试都使用它。

长按 / 多轨按键的“条身”按标准 SV 表现绘制为**两端点位置之间的直杆**：
两端各自位于它们的映射位置，流速造成的压缩、拉伸乃至上下翻转都会如实体现。

## 3. 渲染管线

### 3.0 两种布局

* `LAYOUT_SPLIT`（编辑器默认）：画布左右两个区域，`Layout.pane_6k` 与 `Layout.pane_mouse`
  分别给出边界；`lane_rects` 只落在 6K 区域内，`mouse_left/mouse_right` 是鼠标区域里
  0..1 合法区域的左右界。两个区域共用 `judgment_y` 与 `beat_to_y()`，所以时间轴严格同步。
  6K 区域取 ``SPLIT_6K_RATIO = 0.25``；鼠标区域把 ``MOUSE_OVERFLOW_NORM = 0.45`` 的归一化
  余量分给两侧，于是显示范围是 ``-0.45 .. 1.45``；``norm_to_x()`` 按真实值映射，
  超出显示范围的部分由渲染层与命中测试裁剪到鼠标平面内（只影响显示，不改数据）。
* `LAYOUT_OVERLAY`（没有 pygame 时的演示退路）：`pane_mouse` 直接取中间四条轨道，
  鼠标平面叠加在 6K 上。有 pygame 时演示模式改用 ``game/softview.py``：
  离屏复用游玩器软件渲染，再把整帧贴到画布上。离屏视图的渲染参数由编辑器自己的
  「演示视图设置」给出（`softview.view_settings_for`），与游玩器的 `player.json`
  互相独立、后端固定软件渲染；演示帧不画鼠标指针与 HUD。

`ViewState.set_layout_mode()` 切换时会 `recompute()`；`lane_at()` 在 6K 区域之外返回 `None`，
因此放置类工具天然不会把 6K 物件放到鼠标区域里。

`Scene`（`ui/scene.py`）是一个**带差分的画布封装**：

* 每帧 `begin()` → 用稳定 key 声明图元（`rect/line/polyline/polygon/oval/text`）
  → `end()` 自动删除本帧未出现的图元；
* 图元坐标与选项与上一帧完全相同时**不触碰** Tk 对象，只有变化时才 `coords/itemconfigure`；
* 因此 60 FPS 下的开销只与“变化量”成正比。

场景还维护**显式图层**（`set_layer`）：Tk 画布的对象层级由创建顺序决定，
切换布局时某些对象会被删除再重建，如果不排序，新建的区域底色会跑到最上层把物件盖住。
`Scene.end()` 在检测到重建后按图层号 `tag_raise`，保证
「背景 < 区域底色/轨道 < 网格 < 合法区域与横向网格 < 物件 < 判定线 < 预览 < HUD」
始终成立（`test_layer_order_survives_layout_switch` 覆盖这条约束）。

绘制顺序：背景 → 轨道 → 合法区域边界 → 时间网格 → 横向辅助网格 → 物件
→ 判定线 → 幽灵预览 / 橡皮筋 → HUD 文字（时间轴导航交给右侧的 ttk 竖向滚动条）。

物件内部固定为**七层，自下而上**（`Renderer._draw_notes`）：

```
多轨长按 → 单轨长按 → 多轨单键 → 单轨单键 → 空域 → 滑键 → 鼠标点击按键
```

顺序刻意“从大到小”：即使谱面被有意写成非法重叠（长按里套按键、空域压住按键等），
小按键也压在长按之上，半透明空域与滑键再压上去，鼠标点击按键始终在最顶层，交叠处依然可读。
命中优先级（`geometry._depth`）与这套图层**完全一致**，保证“点到的就是你看到的”。

层内顺序：多轨物件（多轨长按 / 多轨单键）按**跨轨道数从多到少**排序，
跨得越多越先画（越靠下层），于是窄物件不会被宽物件压住。

按键图案（`Renderer._draw_lane_note`）：

| 物件 | 图案 |
| --- | --- |
| 单键 / 多轨单键 | 外侧白色描边矩形 + 内缩 2px 的亮蓝色环 + 中间一条白色横线 |
| 长按 / 多轨长按 | 两侧亮蓝色竖边线 + 中间白色竖线（粗细固定 `theme.note_line_width`，与轨道数无关）+ 开头处一条白色横线；内部不填充 |
| 鼠标点击按键 | 左右两条红色竖线 + 中间一条红色横线（`theme.click_edge`，粗细 = `theme.note_line_width`，与 6K 按键的中心实线一致）+ 中心固定大小的红色实心菱形；横线与菱形都以判定时刻为垂直中点，整体位于**最上层**（`Renderer._draw_click`） |

单键与长按（含长按开头）共用同一条横向范围，**长按的渲染宽度与单键一致**；
游玩器侧同样如此（`game/frame.py` 的 `TAP_VISIBLE_FRACTION`：长按按单键贴图的可见宽度内收）。

物件的可见性有两道判据，二者互不替代：

1. **像素范围**（`_draw_notes` 内按算出的 y / 多边形包围盒剔除）——
   因为流速可正可负，不能用拍差判断远近；
2. **判定时间**（`geometry.note_in_time`）—— 判定线越过物件的判定时刻后不再显示，
   长按与空域按 `tail_beat` 计算。渲染与命中测试共用这条规则；
   视图菜单的「显示更早的物件」可以关掉这条时间过滤（已判过的物件画在判定线下方），
   但判据 1（像素范围）始终生效，屏幕外的物件依然不计算、不绘制。

### 3.1 命中测试复用渲染几何

渲染器每帧把“真正画出来”的物件（已过可见性与显示规则过滤）连同它们的包围盒
（空域还带多边形）写进 `geometry.HitCache`：

* 点击 / 框选（`notes_at` / `notes_in_box`）优先查询这份缓存，只遍历屏幕内的物件；
  缓存命中时每帧成本与“可见物件数”成正比；
* 缓存带**视图签名**（判定线位置、每拍像素、画布尺寸、物件数量），
  视图或谱面一变就失效，此时自动回退到全量扫描，保证结果总是正确的；
* 10000 物件实测：一次命中 74.7 ms（全量）→ **0.010 ms**（缓存）。

网格文字（`_draw_time_grid`）承担“照着填数据”的职责：小节线写「小节 N · 第 M 拍」，
拍线写「第 M 拍」，细分格在间距足够时写小数拍号；密度不足时逐级隐藏，
避免糊成一片。

Tk 画布没有 alpha 通道，半透明用 `stipple`（点阵）模拟：
空域填充 `gray50` + 不透明描边，滑键填充 `gray50` + 不透明箭头，
与规格要求的“半透明填充 + 不透明边界”一致。

空域只画**左右两条边界曲线**（含放置时的幽灵预览），不画上下封口横线：
区域的语义由两条边界曲线定义，封口横线只会在时间起止处形成多余的横线。

空域的边界形状（左右两条曲线）**只在可能显示时才计算**：

1. 先按显示规则（判定时间未过）过滤；
2. 再做便宜的可见性预判 —— 匀速速度组用可视**时间窗** O(1) 排除；
   非匀速组在“速度段边界 + 等分点”上采样判断（每段内位置线性，采样是精确的），
   这一步只算 y；
3. 只有可能可见的空域才去算左右边界曲线（缓动求值 + 坐标变换），
   采样点数还会按屏幕高度自适应（越高越密，最矮时 4 点）。

## 4. 交互状态机

`ToolController`（`ui/interactions.py`）持有唯一的“未完成操作”状态：

| 工具 | 第一次点击 | 第二次点击 | 备注 |
| --- | --- | --- | --- |
| 选择 | 选中 / 开始框选 | 释放时确定框选结果 | Ctrl = 与上次选择做对称差 |
| 单轨按键 | 直接放置 | — | 悬停时显示幽灵 |
| 多轨按键 | 记录起点轨道与时间 | 另一条轨道 → 生成 | 时间以第一次点击为准 |
| 长按 | 记录起点轨道与时间 | 任意位置（含鼠标区域）→ 结束时间 | 期间可滚动 / 缩放 |
| 空域 | 记录开始时间 | 记录结束时间 → 弹出边界设置 | 边界位置允许超出 0..1 |
| 左右滑键 | 记录时间与起始横坐标 | 决定方向与终点 | 开启横向网格时吸附网格线 |
| 鼠标点击按键 | 记录中心位置与时间 | 点旁边定大小 → 生成 | 半径不足最小时按最小值补齐 |

鼠标平面的横向摆放（滑键 / 空域 / 点击按键共用）由 `ToolController._norm_x()` 统一决定：
**启用**横向辅助网格 → `snap_norm()` + 夹进 `0..1`；**未启用** → 直接取
`x_to_norm()` 的真实位置（允许出界）。只有点击落在鼠标平面这块画布区域之外才返回 `None`。

`Esc` 或切换工具会调用 `cancel_pending()` 放弃未完成操作。
粘贴模式（`Ctrl+V` 后）是独立状态，任意点击确定目标时间。

弹出对话框（`ui/dialogs.py::BaseDialog` 及其子类）底部**只有一个确认按钮**
（各对话框自己的 `ok_text`；帮助 / 速度组是「关闭」），取消走 `Esc` / 关闭窗口；
单行输入用 `TextInputDialog`（替代 `tkinter.simpledialog`），同样只有一个确认按钮。
退出前的「未保存修改」询问用 `SaveChangesDialog`，只有「保存 / 不保存」，
`Esc` / 关窗表示放弃这次操作。

## 5. 撤销 / 重做

采用**差量记录式撤销**（`Document.commit(UndoRecord)`）：每条命令记录“怎么撤销、怎么重做”，
只包含**被改动的数据**。

| 命令 | 撤销 | 重做 |
| --- | --- | --- |
| 放置 / 粘贴 | 删除这些新 id | 用保存的数据重建（id 不变） |
| 删除 | 把被删物件的数据写回来 | 再删一次 |
| 镜像 / 编辑物件 / 改速度组归属 | 这批物件的“改动前”数据 | “改动后”数据 |
| 元数据 / BPM 与偏移 / 速度组面板 | 这些轻量结构的旧值 | 新值 |

**视图 / 编辑器设置不进撤销栈**（缩放、网格、延迟、音量、节拍音、侧轨高亮、
显示更早的物件……）：它们存在全局 `settings.json`，改了不产生撤销记录、
不标记谱面已修改；撤销谱面改动时也不会把它们一并回退。

* 每条记录还保存**选择集合的前后状态**，所以撤销/重做后选中范围也会还原；
* 代价：每条记录 O(改动量)（通常几 KB），栈上限提高到 500 步；
* 实测（10000 物件）：一次“编辑 + 撤销”约 **0.7 ms**，撤销栈内存为 KB 级；
* 新增撤销命令时，只需在命令末尾 `commit()` 一条记录（见 `model/document.py`）。

速度组成员在序列化时按 id 排序（`SpeedGroup.to_dict`），因此成员顺序变化不会影响
“撤销前后数据是否一致”的判断，存档结果也可复现。

### 5.1 物件排序缓存

渲染、导出与命中测试都需要“按判定时刻排序”的物件列表（`sort_key = (head_beat, tail_beat, id)`）。
`Chart.sorted_notes()` 会把结果缓存在 `_sorted_cache` 里，只在必要时重建：

* `Chart.add()` / `Chart.remove()` 自动失效；
* `Document.apply()`（放置、删除、粘贴、镜像、编辑物件、改 BPM……）统一失效，
  因此**就地修改**物件时间（例如镜像后再改拍）也不会留下脏缓存；
* 外部直接改物件数据时应显式调用 `Chart.invalidate_order()`；
* 10000 物件实测：每帧排序 1.16 ms → **0.000 ms**（只在编辑后的第一帧重建一次）。

## 6. 音频与延迟补偿

* 后端抽象（`audio.py`）：`PygameBackend`（pygame.mixer.music 流式播放，倍速 1.0x）、
  `StretchedSoundBackend`（numpy 线性插值重采样后分窗口播放；倍速 ≠ 1.0x
  或启用音效混音时使用）、`SilentBackend`（`time.perf_counter()` 时钟，无声音但功能完整）。
* 未安装 pygame / 音频设备打不开时自动退化，状态栏明确提示，不会影响编辑。
* 音效（节拍音 / 打击音）：`metronome.effect_events()` 预先算出整条时间轴上的
  **歌曲毫秒时刻**，`StretchedSoundBackend` 在合成窗口时把到点的音效叠加进输出。
  音效不参与时间伸缩（固定 45ms），输出位置 = `(时刻 − 窗口起点) / 倍速`，
  与歌曲共用一路通道和同一段系统延迟，因此天然对齐；跳转 / 暂停恢复只混起播
  位置之后的时刻，不补发。
* 时刻表**增量维护**（`EditorApp._refresh_effects`）：节拍音 / 打击音两半各有
  缓存键（时间轴与模式 / `Document.revision` 与覆盖范围），改哪一半只重算哪一半，
  改音量、改倍速不触发重算；覆盖范围按 30 秒分桶，无变化的 tick 只比较缓存键。
* 起播 / 往回滚后的裁剪：`_refresh_effects(refilter=True, from_ms=起播毫秒)`
  按**新的起播位置**裁掉过去的条目（用旧暂停位置会把中间整段音效裁没）。
* 播放中改时刻表：变化落在当前窗口**还没播到**的部分时，从当前位置重合成
  当前窗口（音乐接着走、音效立刻生效）；否则只重合成“排队窗口”。
* 播放中改音量：混音模式下歌曲音量烘进缓冲、音效各自带增益，所以同样从
  当前位置重合成当前窗口，立即生效；`set_mix(歌曲音量, 音效增益)` 合并成
  一次入口，“音乐 / 节拍音 / 打击音”一起改只重合成一次。
* 延迟补偿：`audio_latency_ms` 表示“软件执行播放 → 硬件出声”的间隔，
  播放时使用 `后端位置 − 延迟` 作为“耳朵听到的位置”来推进判定线，
  这样屏幕与听到的声音是对齐的；延迟按真实时间计，慢放时按倍速缩放。
* 暂停时：先把当前听到的位置换算成拍并吸附网格，再让音频停在“该拍对应的歌曲位置”，
  保证“继续播放”从判定线所在处接续。

## 7. 数据一致性

* 物件的 `group` 字段与速度组的 `note_ids` 双向记录；
  `Chart._repair_groups()` 在读档后修复不一致（比如手工编辑过的 JSON），
  保证“每个物件一定有归属，且只有一个归属”。
* 默认组（id = 0）永远存在，不可删除；删除其它组时其物件回到默认组。
* 第 0 拍的 BPM 记录与流速记录强制存在（只允许修改），避免除零与未定义区间。

## 8. 性能

* 渲染：差分场景 + 可见区间剔除（视口外的物件不生成图元）。
* 网格：细分线过密时自动降级（时间网格退成拍线 / 小节线；横向网格按间距抽稀，标签更密时隐藏）。
* 速度积分：分段常数求和，O(段数)。
* 音效：时刻表一次算好、按缓存键增量维护（编辑只重算打击音，音量 / 倍速不重算）；
  5000 物件实测“一次编辑 ≈ 3.4ms、无变化的 tick < 0.001ms”。
* 主循环：`after(16, ...)` ≈ 60 FPS；空闲时同样保持轻量（差分命中率极高）。

## 9. 编辑器与游玩器的数据复用

* 游玩器读取同一份 JSON：判定数据就是“判定拍 + 轨道区间 / 区域边界 / 滑动方向”。
* 音频时间轴（拍 ↔ 歌曲毫秒）集中在 `TimingMap`，编辑器与游玩器共用。
* `SpeedGroup` 的位置推算同时服务于编辑器的物件摆放与游玩器的运动画面，
  两边因此保持同一套时间语义（见 `docs/PLAYER.md`）。
  游玩器的 `frame.scroll_ms` / `note_scroll_ms` 就是这套语义（``∫ v·spb dτ``）：
  位置、剔除与同层绘制顺序都用它，流速可正可负时也不会退化成“按拍差排序”。
* 鼠标图案（滑键 / 鼠标点击按键）的竖直中心由 `game/frame.py` 统一给出
  = 鼠标运动平面：点击图案内容占满整张图（`click_center`，可见部分上下各一半）；
  滑键主体 / 箭头贴图是双倍高、下半透明（`slide_center`），可见楔形仍在平面上方。
  游玩器的软件渲染与 Panda3D / OpenGL 路径都从这里取，不会各自偏移。
* 判定线**之前**（z < 0、更靠近摄像头）不是空白：反向流速的物件要在这里出现。
  可视下界由 `PlayerScene.visible_z_near` 估算（相机对两个平面分别二分到画面下缘），
  两个渲染路径都用它做可见性判断，而不是固定余量。
* 判定区间里**已经过去的部分**同样不画：`frame.note_z_span` / `frame.region_samples`
  按当前拍把长按与空域截断（只画当前时刻到结束时刻的一截），空域判定线高亮
  也只在它确实压在判定线上时出现。
